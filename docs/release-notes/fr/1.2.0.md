### À lire avant de mettre à jour

- **Les comptes qui ne sont pas administrateurs ont besoin de droits en plus sur une VM existante**, comme sur
  Proxmox VE. Un compte qui le faisait seulement avec `vm.hardware`, `vm.resize` ou `vm.clone` est maintenant refusé,
  avec le droit manquant dans le message, tant qu'il n'a pas reçu ces droits :
  - ajouter ou agrandir un disque demande `storage.allocate` sur son pool de stockage ;
  - ajouter une interface réseau ou changer son réseau demande `network.assign` sur ce réseau ;
  - cloner une VM demande `storage.allocate` sur le pool de stockage `default`, où le clone est copié.

  Les administrateurs ne sont pas concernés. Ces droits se donnent dans **Utilisateurs et accès › Attributions**.
- **Dans un cluster, mettez à jour tous les nœuds.** Une attribution sur un pool de stockage ou sur un réseau attend
  que chaque nœud ait cette version : un nœud plus ancien ne saurait pas l'enregistrer.

### Nouveautés

- **Console série** dans l'onglet Console d'une VM et dans sa fenêtre de console, à côté de la console graphique et du
  terminal SSH, comme la console xterm.js de Proxmox VE.
  - Elle affiche ce que le système invité écrit sur son port série, et l'invite de connexion qu'il y propose.
  - Elle sert quand le réseau ou l'affichage de l'invité ne fonctionne plus.
  - Une VM sans port série en reçoit un, actif à son prochain démarrage. Toutes les VM créées par Hyperlite en ont
    déjà un.
- **Pools de stockage SMB/CIFS**, comme sur Proxmox VE : le partage d'un serveur Windows ou d'un NAS accueille des
  disques de VM.
  - C'est un stockage partagé, comme un pool NFS : sur tous les nœuds ou ceux choisis, avec la migration à chaud et
    la haute disponibilité.
  - Le mot de passe est gardé dans un fichier lisible par root seulement, sur chaque nœud qui monte le partage. L'API
    ne le renvoie jamais.
  - Le paquet dépend maintenant de `cifs-utils`.
- **Clones liés** : un modèle se déploie en clone lié, créé tout de suite, dont le disque ne garde que ses propres
  changements.
  - Un modèle n'est ni supprimé ni renommé tant qu'une VM lit son disque.
  - La liste des modèles indique les clones liés de chacun.
  - Un clone lié transformé en modèle reçoit un disque à lui.
- **Créer des VM sans être administrateur**, comme vSphere et Proxmox VE le permettent, avec un droit par étape :
  - `vm.allocate` sur le pool de ressources où va la VM : elle y entre, et les droits du pool s'appliquent à elle ;
  - `storage.allocate` sur le pool de stockage de ses disques ;
  - `network.assign` sur son réseau.

  C'est ce dont a besoin, et rien de plus, le jeton d'une chaîne Terraform.
- **Personnaliser une VM créée depuis l'image cloud**, comme les invités de vSphere et de Proxmox VE :
  - son nom d'hôte et son domaine ;
  - des adresses fixes par interface, les autres restant en DHCP ;
  - les serveurs DNS et les domaines de recherche ;
  - une configuration cloud-config à soi (paquets, commandes, fichiers), ajoutée à celle d'Hyperlite.

  À la création, avant le premier démarrage, ou plus tard, au démarrage suivant.
- **Changer le réseau de n'importe quelle interface d'une VM** : elle garde son adresse MAC, que connaissent une
  réservation DHCP et la configuration de l'invité. Seule la première interface le pouvait.
- **Le fournisseur Terraform / OpenTofu officiel** s'appuie sur ces nouveautés. Pour lui, l'API v1 gagne :
  - la lecture seule de chaque objet d'une liste ;
  - la modification sur place des privilèges d'un rôle personnalisé, qui perdait toutes ses attributions quand on le
    supprimait pour le recréer ;
  - `?wait=false` sur la création, le clonage et le déploiement d'une VM, et sur la création d'un modèle : la réponse
    arrive tout de suite avec l'identifiant de la tâche, au lieu d'une requête tenue pendant toute la copie du disque,
    qu'un proxy coupait ;
  - le firmware et la taille du disque de chaque modèle.
- **Le déploiement d'un modèle et la création d'un modèle apparaissent dans Tâches** pendant la copie du disque.

### Corrections

- **Une VM créée sur un autre pool de stockage que `default` n'avait « pas de lecteur cloud-init »** : son onglet
  Cloud-Init ne pouvait changer ni ses clés ni son mot de passe. Pour la même raison :
  - un clone de cette VM démarrait avec le nom d'hôte et les clés SSH de l'original ;
  - son lecteur restait derrière elle quand elle devenait un modèle ;
  - supprimer une VM pouvait effacer une image de la bibliothèque ISO portant le même nom.
- **Sur un nœud neuf, le pool de stockage `default` n'existait qu'après l'ouverture de la page Stockage** : créer un
  volume, y attacher un disque ou y créer un conteneur échouait avant. Il est maintenant créé à sa première
  utilisation.
- **Un pool de stockage qui ne contenait plus que l'image de base d'Hyperlite ne pouvait pas être supprimé.** Supprimer
  une VM rafraîchit aussi les pools qui contenaient ses fichiers : ils listaient encore son disque.
- **Renommer un réseau échouait** sur un nœud sans pilote LXC, qui n'héberge que des VM.
- **Deux créations ou deux déploiements d'une VM sous le même nom en même temps** pouvaient écrire le même fichier
  disque : la seconde est maintenant refusée.
- Trois messages d'erreur collaient deux mots ensemble.

### Sécurité

- **Les fichiers d'identifiants SMB sont vérifiés là où root les écrit.** Seul un fichier `.cred` du dossier des
  identifiants peut être écrit ou supprimé, jamais à travers `..` ou un lien symbolique. L'API validait déjà le nom du
  pool ; le module ne dépend plus de ses appelants pour cela.
